# Python Project Analysis Cookbook

This cookbook defines the analysis workflow for Python projects.

## Phase 1: Framework Detection 🔍

### Detect Framework and Stack

- Use the `detect_framework` tool to identify the project framework
- Tool will check for: Django, Flask, FastAPI, generic Python
- Tool returns: `{"type": "python", "framework": "django", "language": "python"}`

### What to look for:
- requirements.txt or pyproject.toml
- Framework-specific files (manage.py for Django)
- Common packages in dependencies
- Project structure patterns

## Phase 2: Dependencies Analysis 📦

### Analyze Dependencies

- Use the `analyze_dependencies` tool on the project
- Tool reads requirements.txt or pyproject.toml and extracts:
  - Runtime dependencies
  - Version constraints
  - Any dev dependencies (if separated)

### Record:
- Key dependencies and their purposes
- Version specifications
- Any notable or unusual packages

### Common Python Dependencies by Type:

**Web Frameworks:**
- Django, Flask, FastAPI, Tornado

**Testing:**
- pytest, unittest, nose2

**Linting/Formatting:**
- black, ruff, pylint, flake8, mypy

**Data Science:**
- numpy, pandas, matplotlib, scikit-learn

**Database:**
- SQLAlchemy, psycopg2, pymongo, django-orm

## Phase 3: Structure Analysis 🗂️

### Map Directory Structure

- Use the `analyze_structure` tool to intelligently map the project
- Tool categorizes directories:
  - Source code (src/, app/, main package directory)
  - Tests (test/, tests/, *_test.py files)
  - Configuration (setup.py, pyproject.toml, setup.cfg)
  - Documentation (docs/, README.md)
  - Data (data/, datasets/)
  - Scripts (scripts/, bin/)

### Python-Specific Patterns:

**Django Projects:**
- manage.py in root
- Multiple app directories
- settings.py, urls.py, wsgi.py

**Flask Projects:**
- app.py or application.py in root
- templates/ and static/ directories
- Often flatter structure

**FastAPI Projects:**
- main.py typically
- routers/ for route modules
- models/ for data models

**Package Projects:**
- setup.py or pyproject.toml
- src/ or package_name/ directory
- tests/ directory
- README, LICENSE files

### Ignore:
- __pycache__/
- *.pyc, *.pyo files
- .pytest_cache/
- venv/, env/, .venv/
- dist/, build/, *.egg-info/
- .git/

## Phase 4: Entry Points Discovery 🚪

### Find Entry Points

- Use the `find_entry_points` tool to locate main files
- Tool checks:
  - Django: manage.py
  - Flask/FastAPI: app.py, main.py, application.py
  - Generic: __main__.py, main.py
  - Package: setup.py "entry_points" or pyproject.toml "scripts"

### Record:
- Application entry point
- Server/WSGI entry point
- Test runner configuration
- Package entry points

### Common Entry Points:

**Django:**
- manage.py (main entry)
- settings.py (configuration)
- urls.py (routing)
- wsgi.py / asgi.py (server interface)

**Flask:**
- app.py or main.py (application factory)
- wsgi.py (production server)

**FastAPI:**
- main.py (application instance)
- Usually creates `app = FastAPI()`

**CLI Tools:**
- __main__.py in package
- Entry points in setup.py/pyproject.toml

## Phase 5: Pattern Detection 🎯

### Identify Patterns and Architecture

Based on the structure and dependencies, identify:

**Web Framework Patterns:**
- Django: MTV (Model-Template-View)
- Flask: Blueprint-based or simple app
- FastAPI: Router-based API structure

**Testing Patterns:**
- pytest (most common)
- unittest (built-in)
- tox for multi-environment testing
- Coverage tools (coverage.py, pytest-cov)

**Database Patterns:**
- ORM: Django ORM, SQLAlchemy
- Direct: psycopg2, pymongo
- Migrations: alembic, Django migrations

**API Patterns:**
- REST API (Flask-RESTful, Django REST Framework)
- GraphQL (Graphene)
- gRPC

**Code Quality:**
- Linting: pylint, flake8, ruff
- Formatting: black, autopep8, ruff
- Type checking: mypy, pyright

**Async Patterns:**
- asyncio
- FastAPI (async by default)
- Django async views

## Phase 6: Generate Report 📊

### Create Comprehensive Report

- Use the `generate_report` tool with all gathered data
- Tool will format the information into a structured markdown document

### Report Structure:

```markdown
# Project Context: [project-name]

**Generated:** [timestamp]
**Type:** Python
**Framework:** [detected framework]
**Python Version:** [if specified]

## Tech Stack
[Dependencies organized by category]

## Project Structure
[Directory tree with annotations]

## Entry Points
[Main files that start the application]

## Key Dependencies
[Most important packages and their roles]

## Development Setup
[How to set up virtual environment, install deps]

## Patterns Detected
[Architecture patterns, testing, async, etc.]

## Development Workflow
[How to run, test, lint the project]

---
*Generated by Project Context Analyzer*
```

### Output Mode:

- IF: User requested "save" or "save it"
- THEN: Write report to `.project-context.md` in project root
- ELSE: Display report in conversation

## Example Tool Usage Sequence

```
1. detect_framework(".")
   → {"type": "python", "framework": "django", "language": "python"}

2. analyze_dependencies(".")
   → {"runtime": [...], "dev": [...]}

3. analyze_structure(".")
   → {"source": {...}, "tests": {...}, "config": {...}}

4. find_entry_points(".", "django")
   → ["manage.py", "settings.py", "wsgi.py"]

5. generate_report({...all_data...}, output_mode="display")
   → [formatted markdown report]
```

## Success Criteria

- ✓ Framework correctly identified
- ✓ All major dependencies catalogued
- ✓ Directory structure clearly mapped
- ✓ Entry points located
- ✓ Patterns accurately detected
- ✓ Report is clear and actionable
- ✓ Output matches user's request (display or save)

## Notes

- Python projects vary widely in structure
- Focus on what's most important for understanding the project
- Highlight framework-specific patterns
- Note if project uses virtual environment (venv, poetry, pipenv)
- Identify if it's a library/package vs application
- Check for async patterns if using modern Python (3.7+)
